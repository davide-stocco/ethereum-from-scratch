    Hex and bytes

    Permanent. This isn't an Ethereum rule at all — it's how computers represent data.

    Everything on Ethereum is eventually a string of characters like this:

    0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045

    This page is about how to read that. It's short, and it exists so that later pages can say "32 bytes" and have it mean something.

    Byte · hexadecimal

    A byte is eight bits — one of 256 possible values, conventionally read as a number from 0 to 255.

    Hexadecimal, or hex, is base 16: the digits 0–9 plus the letters a–f. One byte is exactly two hex characters, and that single fact is the only reason anyone writes data this way.

    A byte is eight bits

    A bit is a single one or zero. A byte is eight of them in a row:

    0 1 1 0 1 0 0 1

    How many different bytes are possible? Each position is independently a 0 or a 1, so every position you add doubles the number of patterns. Small cases first, because the pattern is easier to see than to state:

    Bits Patterns All of them
    1 2 0 1
    2 4 00 01 10 11
    3 8 000 001 010 011 100 101 110 111
    8 256 00000000 … 11111111

    Each extra bit doubles it: 2, 4, 8, 16, 32, 64, 128, 256. That's 28.

    By convention each pattern is read as a number, counting up from zero:

    00000000  =    0
00000001  =    1
00000010  =    2
00000011  =    3
   ...
11111110  =  254
11111111  =  255

    So "one byte" and "a number from 0 to 255" are two descriptions of the same thing. The byte is the unit everything gets measured in — not because eight is mathematically special, but because it's what hardware settled on, and the whole stack has counted in bytes since.

    How a pattern becomes a number

    The same way a decimal number does, except each position is worth twice the one to its right instead of ten times. So the place values are 1, 2, 4, 8, 16, 32, 64, 128 — the powers of two.

    Take the byte from the top of this section, 01101001. Multiply each bit by its place value and add up:

    0 × 128  =    0
1 ×  64  =   64
1 ×  32  =   32
0 ×  16  =    0
1 ×   8  =    8
0 ×   4  =    0
0 ×   2  =    0
1 ×   1  =    1
            ────
             105

    A bit is either 0 or 1, so each position either contributes its place value or contributes nothing. Reading a byte is just adding up the place values wherever there's a 1: 64 + 32 + 8 + 1 = 105.

    Which also shows where the 0-to-255 range comes from. The largest possible byte is 11111111, every position contributing:

    128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255

    And the smallest is 00000000, contributing nothing at all. Zero to 255, with every value in between reachable exactly once.

    Hexadecimal

    Base 16 needs sixteen digits, and since we only have ten, the first six letters fill in. The encoding is standardised, as Base16 (Josefsson, 2006), though you'll never see it called that outside a specification:

    Hex Decimal Hex Decimal
    0–9 0–9 d 13
    a 10 e 14
    b 11 f 15
    c 12

    So f is 15, and 10 in hex is sixteen.

    Reading a hex number

    Exactly the same trick as the bits above, with a different multiplier. Each position is worth 16 times the one to its right — where in binary it was twice, and in decimal ten times.

    So the place values are the powers of sixteen: 1, 16, 256, 4096. Take 0x2f:

    0x2f
  │└─ f  = 15,  in the ones place      →  15 × 1   =  15
  └── 2  =  2,  in the sixteens place  →   2 × 16  =  32
                                                      ──
                                                      47

    And a four-character example, 0x1234:

    4 × 1     =     4
3 × 16    =    48
2 × 256   =   512
1 × 4096  =  4096
             ─────
              4660

    That's all there is to it. Nothing about hex is conceptually different from decimal — only the number of digits available.

    Try it: convert between decimal, hex and binary

    Type into any field and the other two follow. It starts on 0x1234, the example above.

    Things worth trying:

    • 255, then 256. One byte becomes two, because 255 is the largest value a single byte holds.
    • ff, then 100 in the hex field — the same boundary from the other side.
    • A real address, like 0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045. It reports 20 bytes, and the decimal equivalent is an absurd number nobody would ever want to read. Which is the point of the next section.
    • 10101010 in binary. Note it comes out as aa — each hex character is exactly four bits.

    Why base 16, and not 10

    Because of one tidy coincidence: one byte is exactly two hex characters.

    A byte holds 256 values. Two hex characters give 16 × 16 = 256 possibilities. They correspond perfectly, with nothing left over:

    Bits Hex Decimal
    00000000 00 0
    00001111 0f 15
    00010000 10 16
    10101010 aa 170
    11111111 ff 255

    Notice that two hex characters also split the byte neatly in half: the left character is the first four bits, the right character the last four. aa is 1010 then 1010.

    Decimal has no such alignment, and the consequence matters.

    To see why, put yourself on the receiving end. A program sends you some characters and tells you they're three bytes. Your job is to work out what those three bytes were — and you don't know their values in advance. That's the whole task.

    In hex, every byte is two characters, whatever its value:

    The byte In hex
    5 05
    255 ff
    7 07

    So it arrives as six characters:

    05ff07

    Six characters, two per byte, three bytes. Cut after every second character and you're done: 05 ff 07. And that procedure would have worked for any three bytes, which is the important part.

    In decimal, how many digits a byte takes depends on its value:

    The byte In decimal Digits
    5 5 one
    255 255 three
    7 7 one

    So it arrives as five characters:

    52557

    Now where do you cut? You have five characters to divide into three bytes, and several ways to do it are perfectly legal:

    Reading Bytes Valid?
    5 25 57 5, 25, 57 yes — all ≤ 255
    52 5 57 52, 5, 57 yes
    5 255 7 5, 255, 7 yes — the right one
    52 55 7 52, 55, 7 yes

    Four readings, all legitimate, and nothing in the string tells you which was meant. To know that each byte took one, three and one digits, you'd have to already know the values — which is precisely what you were trying to find out.

    That's the alignment hex has and decimal hasn't. In hex the boundaries are implied by position, because every byte is the same width. In decimal they aren't implied at all, so they'd have to be sent separately — and at that point you've invented a worse version of hex.

    d8 dA 6B F2 69 64 aF 9D 7e Ed 9e 03 E5 34 15 D3 7a A9 60 45

    That's the address from the top of the page, as the twenty bytes it actually is.

    Hex is also case-insensitive as a number — aF and AF are the same value. (Mixed case in an address does carry meaning, but as a checksum rather than as part of the number. That's covered under addresses.)

    The 0x prefix

    0x means "what follows is hexadecimal". That's all. It is not part of the value — it's a label, so that 0x11 isn't mistaken for eleven.

    The convention comes from the C programming language and is used nearly everywhere. Ethereum tooling puts it on essentially everything.

    The two lengths worth memorising

    Almost every long string you meet on Ethereum is one of two sizes:

    Bytes Hex characters What it usually is
    20 40 an address
    32 64 a hash, or one slot of contract storage

    Worth doing once, by hand: count the characters after the 0x in the address above. There are forty. That's twenty bytes, and from now on "20 bytes" and "40 hex characters" should feel like the same statement.

    The 32-byte figure turns up constantly because it's the output size of Keccak-256, Ethereum's hash function, and also the width of a single machine word in the EVM.

    One trap worth knowing about

    0x1234 can mean two different things, and conflating them causes real bugs.

    As a number, it's 4660 — the calculation from earlier.

    As bytes, it's two bytes: 0x12 and 0x34.

    Both readings are valid. Which is meant depends on context — and the context is really what you intend to do with it.

    A number is a quantity. You add to it, subtract from it, ask whether it's bigger than another one. A balance is a quantity: 2.5 ether plus 1 ether is a meaningful thing to compute.

    A byte string is an identifier. You compare it for equality and you check its length. That's all. An address isn't a quantity — the only questions worth asking are "is this 20 bytes?" and "is this the same address as that one?"

    Which is why "is this address larger than that address?" is not a meaningful question, even though both look like enormous numbers. It's the same category error as asking whether one phone number is bigger than another: the digits are there to identify, not to count.

    So: balances are numbers. Addresses, hashes and storage keys are byte strings. Nothing good comes of doing arithmetic on the second group.

    Leading zeros, and why they sometimes matter

    The distinction above has a sharp edge: as a number, leading zeros are meaningless; as bytes, they are not.

    0x01 and 0x0001 are the same number — one. But they are different byte strings: one byte versus two. So a 32-byte hash beginning 00 has not somehow lost a byte, and padding a value to 32 bytes changes its length without changing its value.

    This matters more than it sounds. RLP requires that integers be encoded with no leading zeros, precisely so that each value has exactly one valid encoding. Without that rule, 0x01 and 0x0001 would both be valid encodings of the same number, two nodes could hash the same data and get different answers, and consensus would break.

    So "is this a number or a byte string?" isn't pedantry — the answer determines whether 0x0001 is well-formed.

    Big-endian, and why the direction is a choice

    Here's the problem. Take the two bytes 0x12 and 0x34, in that order, and read them as one number. There are two defensible answers, because you first have to agree which end carries the large part.

    Big-endian treats the first byte as the most significant:

    0x12 × 256  +  0x34        =  18 × 256 + 52  =  4660

    Little-endian treats the last byte as the most significant, so the same two bytes are read in the other order:

    0x34 × 256  +  0x12        =  52 × 256 + 18  =  13330

    Same bytes on disk. Two different numbers. Which is why it has to be agreed rather than assumed.

    Ethereum is big-endian — integers are serialised most-significant-byte first throughout the specification (Wood, 2014).

    The convenient consequence is that hex strings read in the direction you already expect. In decimal 1234, the leftmost digit carries the largest place value; big-endian does the same thing with bytes, so 0x1234 is 4660, exactly as the place-value calculation earlier gave.

    You can go a long way without thinking about this. It becomes unavoidable the moment you write code converting between numbers and bytes, which is where most beginner mistakes in this area live.

    Why not binary?

    You could write everything in bits, and occasionally that's clearer — it's the only way to see a single flag being set.

    But bits are unmanageably long. The address at the top of this page is twenty bytes, which is 160 bits:

    1101100010011010011010111111001001101001011001001010111110011101...

    Forty hex characters, or a hundred and sixty ones and zeros. Hex is the compromise: compact enough to read aloud, and still exactly aligned to byte boundaries.

    Recap

    • A byte is 8 bits, holding one of 256 values.
    • Hex is base 16, using 0–9 and a–f.
    • One byte is exactly two hex characters — the reason hex is used at all.
    • 0x means "hex follows" and isn't part of the value.
    • 20 bytes = 40 characters = an address. 32 bytes = 64 characters = a hash.
    • Whether a hex string is a number or a byte string is a real distinction, and leading zeros are where it bites.
