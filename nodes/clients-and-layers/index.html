    Clients and the two layers

    Mostly permanent. How the work of a node is divided, and why several independent implementations of it exist on purpose, are both structural. Which particular implementations exist is not.

    Current as of Fusaka (December 2025)

    Which implementations exist, who maintains them, and what share each has will all have moved by the time you read this — teams start and stop. So this page names roles and reasons rather than products, and any figure that does appear carries its date.

    Client

    The software that implements Ethereum's rules. Not an app, not a wallet — the program itself.

    So node and client are not two words for one thing. A node is what a machine does: hold the state, check every arriving block, reject anything invalid. A client is the program it runs in order to do that. The same relation as web server and the particular software serving the pages.

    Several independent clients exist, written by different teams in different programming languages. They must agree exactly, because a disagreement about the rules is a disagreement about what happened.

    One node, two programs

    Now the complication. A node doesn't run one client — it runs two, side by side, and needs both.

    They do different jobs, and neither can do the other's. One holds the accounts and checks what the transactions did; the other works out which block comes next. They talk to each other over a defined interface, and the pair of them is what makes one node.

    The execution client is the state machine this site has been describing. It holds the accounts, runs contract code, keeps the state, and checks that transactions follow the rules.

    The consensus client works out which block comes next — the problem that has to be solved by somebody because the rules don't settle it. It talks to other nodes' consensus clients, and tells its own execution client which block to apply.

    Neither is a node by itself. The execution client can check whether a block is valid but has no opinion about which block is the real one. The consensus client can tell you which block the network has agreed on but cannot check whether its contents make sense. A node is the pair.

    History: they were separate systems first

    The division looks like an architectural decision. It's a historical accident that turned out well.

    Until 2022, Ethereum did both jobs in one program: one piece of software held the accounts and also ordered the transactions, by mining. Meanwhile a second, entirely separate network — the Beacon Chain — had been running since December 2020, doing nothing but practising consensus. It held no accounts and processed no transactions. For about twenty-one months it ran alongside the real thing, agreeing on the order of nothing in particular.

    In September 2022 the two were connected: the old system stopped ordering transactions and started taking its order from the Beacon Chain instead. EIP-3675 (Kalinin et al., 2021) is the specification for that change, and the event is called the Merge.

    Which is why the split exists at all. Nobody set out to build a node from two programs; two systems were built separately and then joined, and the seam is still visible in every node today.

    Why several of each, rather than one official one?

    Here is the part worth understanding, because the obvious intuition is backwards.

    It would seem simpler — and safer — to have one correct implementation that everybody runs. One codebase to audit, one team to fund, no risk of two programs disagreeing about the rules.

    That arrangement has a fatal property: a bug in it is a bug in Ethereum.

    If every node runs the same software and that software accepts a block it shouldn't, every node accepts it. There is no one left to notice. The rules of Ethereum would no longer be the specification — they would be whatever that program happened to do, bugs included, and nobody could tell the difference.

    Several independent implementations change the shape of that failure. A bug in one is a disagreement rather than a catastrophe: the affected nodes reject blocks the others accept, the discrepancy is visible immediately, and the remaining network carries on. The bug becomes a problem for that client's users instead of a rewriting of the rules.

    So diversity here is a safety property, not an absence of standardisation. The duplicated effort is the point, in the same way a second opinion is not an inefficiency.

    How real is that risk?

    Not hypothetical, and not rare enough to be reassuring.

    Researchers at Seoul National University and Georgia Tech built a tool that feeds the same transactions to different clients and watches for disagreement — differential fuzzing. It found two previously unknown consensus bugs in a single widely used client, and one of them later caused a split on the live network (Yang et al., 2021).

    That one sentence contains the whole argument. The bugs existed. They were found by comparing implementations against each other, which is only possible if more than one exists. And one of them went on to do real damage anyway.

    The sharp edge: when one client has most of the network

    Diversity is only protective if it exists in practice, and it hasn't always.

    On 11 November 2020, a consensus bug in the client then running most of the network caused exactly the failure described above. A fix had been released earlier but not flagged as urgent, so many operators hadn't applied it. A single transaction triggered the bug, and nodes on the old version split away from the rest — following a different chain, reporting different balances, and in some cases serving wrong answers to the applications built on them (De, 2020).

    Two things about that incident are worth separating, because they're usually run together.

    It was a version split, not a client-diversity failure in the strict sense — old and new releases of the same client disagreed. But the reason it mattered so much is dominance: because one implementation held most of the network, a mistake in its release process became most of the network's problem.

    And this is why client share is counted and published. It isn't a popularity contest. Under proof of stake the thresholds become sharper still — a client with a large enough share of validators can stall the network's ability to settle anything, or in the worst case carry an invalid chain to settlement. The exact fractions are parameters and belong on that page; the structural point is that share is a safety variable, and a client being popular is a risk rather than an endorsement.

    Who writes them, and who pays?

    A fair question once "nobody is in charge" is taken seriously, and the answer is less tidy than people expect.

    Each client is built and maintained by its own team, independently, in different languages, funded variously — foundation grants, company sponsorship, public goods funding, and in some cases unpaid work. No team can compel the others to do anything. The specification is the shared reference, and agreeing with it is voluntary in the sense that nothing but consequence enforces it.

    Which produces a situation worth stating plainly: the rules of Ethereum are maintained by several small groups of people who are not obliged to continue. Who decides what those rules become is a different question again, and gets its own page.

    Do you ever choose a client?

    Running a node: yes, and it's the one decision an individual operator makes that affects everybody else. You pick one execution client and one consensus client. Choosing a less common one slightly increases your own risk — fewer users means bugs are found later — while reducing the network's. That tension is real and worth naming rather than smoothing over.

    Using Ethereum through a wallet: no. You're relying on somebody else's node, running somebody else's client, chosen by them. The previous page made this point about nodes; it applies one level down as well. Most people have never chosen a client and never will, which is precisely why the share figures matter to people who aren't running anything.

    Recap

    • A node is two programs: an execution client holding the accounts, state and code, and a consensus client deciding the order and voting on blocks. Neither program is a node alone.
    • The split is historical, not architectural. The consensus system ran as a separate chain from December 2020 and was joined to the execution system in September 2022 — the Merge.
    • A client is an implementation of the rules — the program, not the machine. Several independent ones exist for each of the two jobs, written by different teams in different languages.
    • One official implementation would be more dangerous, not safer. If everyone runs the same software, a bug in it isn't a bug — it silently becomes the rules.
    • With several, a bug is a disagreement rather than a rewriting: visible immediately, survivable by the rest of the network. The duplicated effort is the point.
    • The risk is documented: differential fuzzing across clients found two unknown consensus bugs in one client, and one later split the live chain.
    • Dominance is the danger. In November 2020 a bug in the most-used client split the network, which is why client share is treated as a safety variable rather than a popularity measure.
    • Clients are maintained by independent, variously funded teams that nothing obliges to continue.
    • Running a node means choosing clients; using a wallet means somebody chose for you.
